# Orchestrator Worker Pattern

## 1. Quick Summary

| Area | Details |
|---|---|
| Topic | Orchestrator Worker Pattern |
| Difficulty | Intermediate |
| Used For | Handling complex requests that require multiple distinct skills to run in parallel or sequence. |
| Common Mistake | Making the orchestrator do actual work instead of just planning and routing. |
| Performance | Evaluated based on token usage and latency. |

## 2. Engineering Story

Bro, imagine you are a senior engineer deployed to a client site. The client wants a system that can handle a wide variety of customer requests, from billing inquiries to technical support. Instead of trying to build one giant agent that knows everything, you decide to build a central 'router' agent that analyzes the request and delegates it to a specialized 'worker' agent.


Bro, your company needs an AI system to process incoming emails, categorize them, extract attachments, and update a CRM. You build a pipeline where Agent A passes to Agent B, which passes to Agent C. But if Agent B fails, the whole pipeline stalls, and Agent A has no idea what happened. Linear pipelines are brittle. Instead, you need to implement the Orchestrator-Worker pattern. In this architecture, a central Orchestrator agent breaks down the complex task, dispatches sub-tasks to specialized Worker agents, monitors their progress, and handles failures dynamically. This hub-and-spoke model is highly resilient, allowing the orchestrator to retry failed tasks or route them to different workers, ensuring the overall job gets done.

## 4. Concept Explanation

In this pattern, the Orchestrator receives the user prompt, formulates an execution plan, and calls specialized Worker agents as tools. The workers execute their specific tasks (e.g., search web, write code) and return the results to the Orchestrator. The Orchestrator synthesizes the final response.

## 5. Syntax Table

| Role | Responsibility |
|---|---|
| Orchestrator | Planning, Delegation, Synthesis. |
| Worker | Execution, Tool calling, specific domain logic. |

## 6. Beginner Example

```typescript
async function orchestrator(query) {
  const plan = await plannerAgent.run(query);
  const data = await searchWorker.run(plan.step1);
  const code = await codeWorker.run(data);
  return await synthesisAgent.run(code);
}
```

## 7. Real-World Engineering Example

```typescript
import { Agent } from "my-framework";

const webScraperWorker = new Agent({
  name: "WebScraper",
  instructions: "You scrape websites and return raw text.",
  tools: [scrapeTool]
});

const orchestrator = new Agent({
  name: "Orchestrator",
  instructions: "You are the project manager. Break down the user query and use your workers to get the data. Do NOT browse the web yourself.",
  // Workers are passed in as callable tools!
  tools: [webScraperWorker.asTool()]
});

const result = await orchestrator.execute("Summarize the latest news on AI.");
```

## 10. Top Interview Questions

| Question | Answer |
|---|---|
| Why treat workers as tools? | It allows the orchestrator to use standard function calling to trigger complex multi-step processes. |
| What is the bottleneck? | The orchestrator's context window filling up with raw worker outputs. |

## 11. Tricky Questions & Edge Cases

Bro, if a worker returns a 10,000-word essay, the Orchestrator will run out of tokens instantly. Workers must summarize their outputs or pass references (like file paths) back to the Orchestrator.

## 12. Real-World Usage

### Advanced Orchestrator Considerations

While the Orchestrator-Worker pattern simplifies task distribution, the orchestrator itself can easily become a single point of failure or a critical performance bottleneck.

If the orchestrator is overwhelmed with managing state, delegating tasks, and synthesizing results, the overall system latency will spike.

To build a highly scalable orchestrator, consider these advanced concepts:

1. **Stateless Orchestration:** Offload the memory and conversation state to an external database (like Redis or PostgreSQL). The orchestrator should simply wake up, read the state, dispatch the next worker, and go back to sleep.
2. **Asynchronous Dispatching:** The orchestrator should not block while waiting for a worker. It should fire off tasks asynchronously and use callbacks or webhooks to resume when the workers finish.
3. **Dynamic Worker Scaling:** In cloud environments (like AWS or Kubernetes), the orchestrator can dynamically provision new worker instances if a large batch of sub-tasks is detected, shutting them down to save costs once the batch completes.

By optimizing the orchestrator, you ensure the agent team can scale horizontally to handle massive parallel workloads.

| Directive | Instruction | Rationale |
|---|---|---|
| Orchestrator Simplicity | The orchestrator agent must only be responsible for planning and delegation. Do not give it execution tools. | Mixing planning and execution in the orchestrator degrades its routing accuracy and increases latency. |
| Worker Isolation | Worker agents should not communicate directly with each other. All results must be returned to the orchestrator. | Direct worker-to-worker communication bypasses the orchestrator's control flow, making the system unpredictable. |
