# Sessions & State in Google ADK

## 1. Quick Summary
| Area | Details |
|---|---|
| Topic | Sessions & State in Google ADK |
| Difficulty | Intermediate |
| Used For | Persisting multi-turn chat history for ADK Agents securely. |
| Common Mistake | Storing session objects in global memory, which leaks context between concurrent users. |
| Performance | Very fast locally, dependent on Firestore latency when running distributed. |

## 2. Engineering Story

Bro, imagine you are a backend engineer debugging a multi-tenant support bot where User A is suddenly receiving answers based on User B's context. You realize you failed to isolate ADK Session objects per user request, leading to catastrophic cross-user state leakage.

Imagine you deployed a support bot. User A says "My name is Alice." User B says "What is my name?" and the bot replies "You are Alice!"
This is the nightmare of stateless agents in a concurrent web server. Because the developer stored the conversation history in a global python list, every user was reading the same memory. By switching to Google ADK's `Session` manager backed by Firestore, you isolate every user's chat history via a unique UUID, ensuring privacy and eliminating context leaks.

## 4. Concept Explanation

LLMs are completely stateless. To have a conversation, you must pass the entire chat history in every single API call. Google ADK abstracts this using the `Session` object. A session automatically appends the user's prompt, the LLM's response, and any intermediate Tool calls (function calling) to an internal message array. In production, ADK connects this session directly to Google Cloud Firestore or BigQuery to persist it across server restarts.

## 6. Beginner Example

A local session using in-memory state. Great for quick testing, terrible for production.

```python
from google_adk import Agent

agent = Agent(model="gemini-1.5-pro", name="Helper")

# Automatically creates an in-memory session with a random UUID
session = agent.create_session()

response1 = session.chat("My favorite color is Blue.")
print(response1.text)

response2 = session.chat("What is my favorite color?")
# The agent remembers because the Session appended the previous turn automatically.
print(response2.text) # "Your favorite color is Blue."
```

## 7. Real-World Engineering Example

In production (e.g. on Cloud Run), containers die and restart constantly. You MUST persist the session to a database like Firestore.

```python
from google_adk import Agent
from google_adk.storage import FirestoreSessionStorage

# Configure GCP Firestore to hold all conversation state
storage = FirestoreSessionStorage(
    project_id="my-gcp-project",
    collection_name="adk_sessions"
)

agent = Agent(model="gemini-1.5-pro", name="Support")

# When the user logs in, we grab their unique ID
user_session_id = "user_uuid_9921"

# The ADK pulls their historical state from Firestore automatically!
session = agent.create_session(
    session_id=user_session_id, 
    storage=storage
)

# Continues the conversation from where they left off yesterday
response = session.chat("Did you check on that refund status?")
```

## 10. Top Interview Questions
| Question | Answer |
|---|---|
| Why do LLM agents need sessions at all? | Because LLMs APIs are RESTful and stateless. Without sessions, they have no memory of the previous prompt. |
| What is the danger of large sessions? | As a conversation gets longer, the token count increases linearly. This drives up latency and costs, and eventually hits the model's context window limit (though Gemini 1.5 Pro has 2M tokens). |
| How does ADK handle tool execution state? | The session array stores not just text, but `FunctionCall` and `FunctionResponse` objects, allowing the LLM to know exactly what tool it ran 3 turns ago. |

## 11. Tricky Questions & Edge Cases

Bro, how do you handle a session that exceeds the LLM context window?
You must implement **Memory Summarization**. The ADK allows you to hook into the session lifecycle. If the history exceeds a certain token threshold, you trigger a background agent to read the 50 messages, summarize them into 1 paragraph, delete the 50 messages, and prepend the summary to the session.

## 12. Real-World Usage

- **Customer Support Dashboards**: Storing session state in Firestore allows human agents to open the dashboard and instantly read the transcript of what the AI bot discussed with the user.
- **Multi-Day Workflows**: A user asks an agent to run an analysis on Friday. On Monday, they log back in and type "where are we at?". The agent remembers the Friday context perfectly.

## 13. Best Practices
| DO | DON'T |
|---|---|
| Use external persistence (Firestore/Redis) in production | Rely on Python memory (dicts/lists) in a web framework |
| Generate unique, unguessable Session IDs (UUIDv4) | Use predictable session IDs like `user_1`, leading to IDOR vulnerabilities |
| Clear old sessions to save DB costs | Let dead sessions sit in Firestore forever |

## 14. Production Notes
> Production Note:
> Never log raw session histories to standard console logs without redacting PII. If your user types their credit card into the bot, and the Session object saves it to Firestore and Cloud Logging, you just violated PCI compliance. Use GCP Data Loss Prevention (DLP) API to scan and redact inputs before they hit the session state.

## 17. Advanced Session Architecture
1. **Branching Sessions**: Sometimes a user wants to explore a "what-if" scenario without ruining the main conversation. Advanced ADK usage allows you to "fork" a session ID, cloning the history into a new Firestore document, letting the user explore a tangent safely.
2. **System Prompt Injection**: Sessions only track the dynamic conversation. If you need to update the agent's behavior mid-session (e.g. the user upgraded to a premium plan), you must update the core Agent's `system_instruction` independently of the session history.

## 15. Common Mistakes
- **Leaking Context**: Re-using the same `session` object variable in a global FastAPI route.
- **Ignoring Size Limits**: Letting a session grow to 1 million tokens, making every single chat turn cost $5 in Gemini API fees.

## 18. AI Agent Instructions

| Directive | Instruction | Rationale |
|---|---|---|
| Session Isolation | Never share a single `Session` object globally across different HTTP requests or users. | Prevents cross-tenant data leakage and severe privacy violations in multi-user deployments. |
| Memory Pruning | Implement a custom state pruner or sliding window strategy if the session history grows unbounded. | Prevents Vertex AI `400 Bad Request` errors caused by exceeding the maximum context window of the Gemini model. |
| State Persistence | Serialize and store the `Session` history in a persistent database (e.g., Firestore) between stateless Cloud Run requests. | Ensures conversation continuity across container restarts and distributed load balancers. |
