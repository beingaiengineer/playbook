# Multi-Agent Orchestration in Google ADK

## 1. Quick Summary
| Area | Details |
|---|---|
| Topic | Multi-Agent Orchestration in Google ADK |
| Difficulty | Advanced |
| Used For | Building teams of specialized AI agents that route tasks to each other. |
| Common Mistake | Creating an infinite loop where Agent A routes to Agent B, and Agent B routes back to Agent A. |
| Performance | Scales horizontally but introduces network latency on handoffs. |

## 2. Engineering Story

Bro, you built an IT support bot. At first, it just answered password reset questions. Then management wanted it to also write SQL queries to check employee PTO, and also draft HR emails. You jammed all 50 tools into a single Gemini agent. The result? The agent got confused, hallucinated, and accidentally emailed the CEO's PTO balance to the entire company. 
This is why you use multi-agent orchestration. Instead of one massive "God Agent," you build three tiny, specialized agents: `IT_Agent`, `SQL_Agent`, and `HR_Agent`. You put a `RouterAgent` in front of them. When a user asks about PTO, the Router securely hands off the conversation to the `HR_Agent`, which only has access to HR tools.

## 4. Concept Explanation

Google ADK provides native orchestration patterns powered by Vertex AI. Unlike LangGraph, which requires you to manually define nodes and edges in a state graph, Google ADK uses a declarative approach. You define a pool of specialized `Agents`, and you instantiate an `Orchestrator` or a `Router`. The orchestrator uses the LLM to dynamically decide which agent should handle the current turn, automatically transferring the `Session` state so the specialist has full context.

## 6. Beginner Example

A simple router that decides between two agents.

```python
import google_adk as adk

# 1. Define highly scoped agents
researcher = adk.Agent(
    name="Researcher",
    system_instruction="You only search the web for facts."
)

writer = adk.Agent(
    name="Writer",
    system_instruction="You only write poetic summaries."
)

# 2. Create the Orchestrator
team = adk.Orchestrator(
    agents=[researcher, writer],
    default_agent="Researcher"
)

# The Orchestrator automatically decides researcher -> writer
result = team.execute("Find out who won the 2022 World Cup and write a poem about it.")
print(result)
```

## 7. Real-World Engineering Example

In enterprise, you don't use synchronous routers for everything. For heavy tasks, you orchestrate agents via Google Cloud Pub/Sub, passing messages asynchronously.

```python
from google_adk import Agent, Session
from google_cloud import pubsub_v1

# Triage agent processes the initial user request
triage_agent = Agent(name="Triage", model="gemini-1.5-flash")

def handle_incoming_ticket(ticket_text, session_id):
    session = Session(session_id)
    classification = triage_agent.run(f"Classify this ticket: {ticket_text}")
    
    # Asynchronous handoff via Pub/Sub
    publisher = pubsub_v1.PublisherClient()
    
    if classification.text == "BILLING":
        topic_path = publisher.topic_path("my-project", "billing-agent-queue")
    else:
        topic_path = publisher.topic_path("my-project", "tech-support-queue")
        
    # Send the session ID so the next agent can resume the context
    publisher.publish(topic_path, session_id.encode("utf-8"))
    return "Your ticket has been routed to a specialist."
```

## 9. Performance Table
| Pattern | Latency | Complexity | Use Case |
|---|---|---|---|
| Router | Medium (2 LLM calls) | Low | Simple Triage |
| Supervisor | High (N LLM calls) | High | Code Generation / Review |
| Pub/Sub Handoff | Asynchronous | Very High | Long-running background tasks |

## 10. Top Interview Questions
| Question | Answer |
|---|---|
| What is the danger of giving one agent 50 tools? | "Context dilution." The LLM gets confused, token usage explodes, and security risk increases. Multi-agent architecture fixes this. |
| How does ADK handle agent handoffs? | Through native `Router` and `Orchestrator` classes that manage state transfer implicitly via the shared `Session` object. |
| What is the advantage of ADK over LangGraph here? | Tighter integration with GCP IAM and Vertex AI out-of-the-box. LangGraph requires manually wiring up state schemas and graph edges. |

## 11. Tricky Questions & Edge Cases

Bro, what happens if Agent A routes to Agent B, but Agent B doesn't know the answer and routes back to Agent A?
This is a **Routing Loop**. Google ADK mitigates this by enforcing `max_hops` (usually 3 or 5). If the agents pass the context back and forth too many times, the Orchestrator throws a `MaxHopsExceeded` exception to save your API bill.

## 12. Real-World Usage
- **Software Engineering Teams**: A "Coder Agent" writes the python script, hands it to a "Tester Agent" which runs the script, which hands it back to the "Coder Agent" with the error logs to fix.
- **Financial Auditing**: A "Document Extraction Agent" pulls data from PDFs, routes it to a "Validation Agent" to check math, which routes to a "Formatting Agent".

## 13. Best Practices
| DO | DON'T |
|---|---|
| Give specialized agents exactly 1-3 tools | Build a "God Agent" with 50 tools |
| Use asynchronous queues (Pub/Sub) for slow agents | Block an HTTP request waiting for 4 agents to finish |
| Set a hard limit on `max_hops` | Let agents loop infinitely |

## 14. Production Notes
> Production Note:
> Tracing a request through 5 different agents is a nightmare. You must pass a single `correlation_id` through every agent invocation. When using Google ADK in production, inject the `correlation_id` into Cloud Logging so you can query exactly which agent failed in a complex chain.

## 17. Advanced Orchestration Patterns
1. **The Supervisor Pattern**: Instead of agents handing off linearly, you create a Supervisor Agent. The Supervisor looks at the task, breaks it down into sub-tasks, assigns them to Worker Agents in parallel, waits for all results, and synthesizes the final answer. Google ADK supports this via `asyncio` `gather` combined with multiple agent runs.
2. **Dynamic Tool Provisioning**: Instead of hardcoding tools into an agent, a highly advanced Orchestrator can query a Datastore of available tools, and inject only the necessary tools into the Worker Agent at runtime before handing off the task.

## 15. Common Mistakes
- **Shared State Corruption**: Allowing two agents to modify the exact same `Session` object concurrently in separate threads without locks.
- **Ignoring Fallbacks**: Not providing a fallback response if the Router Agent fails to match the user's intent to any of the available sub-agents.
