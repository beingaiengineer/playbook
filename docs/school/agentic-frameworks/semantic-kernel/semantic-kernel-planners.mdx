# Semantic Kernel Planners

## 1. Quick Summary
| Area | Details |
|---|---|
| Topic | Semantic Kernel Planners |
| Difficulty | Advanced |
| Used For | Allowing the LLM to autonomously create a multi-step execution plan from a library of available plugins. |
| Common Mistake | Giving a planner 50 complex plugins and expecting it to formulate a perfect plan without hallucinations. |
| Performance | Slower execution time due to the upfront LLM generation of the plan before execution begins. |

## 2. Engineering Story

Bro, you built an AI that can write emails (Plugin A), search Jira (Plugin B), and calculate math (Plugin C). A user asks: "Find how many Jira tickets are assigned to me, divide that by 5, and email my boss the result."
Without a Planner, you have to write rigid Python `if/else` logic to chain these plugins together. It's a nightmare. 
With a **Semantic Kernel Planner**, you just give the Kernel the user's goal. The Planner (acting as the LLM's brain) looks at all the plugins you loaded, writes a "plan" (like a mini-script), and then executes it step-by-step. It figures out the orchestration completely autonomously.

## 4. Concept Explanation

A Planner takes a user's goal and returns a `Plan` object. This plan is an executable graph of Kernel Functions.
Historically, SK had multiple planners (Sequential, Action). Now, the most powerful planners are:
1. **Handlebars Planner**: Uses the LLM to generate a Handlebars template script representing the steps, which SK then executes safely.
2. **FunctionCallingStepwisePlanner**: Relies on modern OpenAI Tool Calling features to execute steps dynamically, evaluating the result of step 1 before deciding on step 2 (similar to ReAct).

## 5. Syntax Table
| Concept | Code | Description |
|---|---|---|
| Create Planner | `planner = FunctionCallingStepwisePlanner()` | Initializes the planner logic. |
| Generate Plan | `result = await planner.invoke(kernel, goal)` | Creates and executes the plan in one step. |
| Handlebars Planner | `planner = HandlebarsPlanner()` | Uses Handlebars syntax for templated orchestration. |

## 6. Beginner Example

Using a modern Stepwise Planner to solve a multi-step problem.

```python
import asyncio
import semantic_kernel as sk
import semantic_kernel.connectors.ai.open_ai as sk_oai
from semantic_kernel.planners import FunctionCallingStepwisePlanner, FunctionCallingStepwisePlannerOptions
from semantic_kernel.core_plugins import MathPlugin, TimePlugin

async def main():
    kernel = sk.Kernel()
    kernel.add_service(sk_oai.OpenAIChatCompletion(service_id="default", ai_model_id="gpt-4o", api_key="KEY"))
    
    # Load Plugins
    kernel.import_plugin_from_object(MathPlugin(), "Math")
    kernel.import_plugin_from_object(TimePlugin(), "Time")
    
    # Setup the Planner
    options = FunctionCallingStepwisePlannerOptions(max_iterations=5)
    planner = FunctionCallingStepwisePlanner(service_id="default", options=options)
    
    # The Goal requires BOTH plugins!
    goal = "What is the current year added to 50?"
    
    # The planner figures out: 1. Call TimePlugin.year 2. Call MathPlugin.add
    result = await planner.invoke(kernel, question=goal)
    print(f"Final Answer: {result.final_answer}")

asyncio.run(main())
```

## 7. Real-World Engineering Example

In enterprise, you use the `HandlebarsPlanner` when you want a deterministic plan generated upfront that you can log or inspect before executing.

```python
import semantic_kernel as sk
from semantic_kernel.planners.handlebars_planner import HandlebarsPlanner

async def generate_and_execute_plan(kernel: sk.Kernel, user_goal: str):
    planner = HandlebarsPlanner()
    
    # 1. Generate the plan (Does NOT execute it yet)
    # The LLM writes a Handlebars script using the available plugins
    plan = await planner.create_plan(kernel, user_goal)
    
    print("Generated Plan Script:\n", plan)
    
    # 2. You could pause here and ask a human to approve the plan!
    
    # 3. Execute the Handlebars plan
    result = await plan.invoke(kernel)
    return result
```

## 9. Performance Table
| Planner Type | Speed | Adaptability | Cost |
|---|---|---|---|
| Handlebars Planner | Medium (Generates upfront) | Low (Breaks if an early step fails) | Low (1 LLM call to plan) |
| Stepwise Planner | Slow (Evaluates every step) | High (Can self-correct) | High (N LLM calls) |

## 10. Top Interview Questions
| Question | Answer |
|---|---|
| What is the primary risk of using a Planner? | Hallucination. If you have 50 plugins, the LLM might get confused and try to call a `WeatherPlugin` with the wrong arguments. |
| What is the difference between Handlebars and Stepwise planners? | Handlebars creates the entire plan upfront and then executes it (DAG style). Stepwise executes one step, observes the result, and then decides the next step dynamically (ReAct style). |
| How do planners know what plugins are available? | The Kernel extracts the names, descriptions, and type-hints of all imported plugins and injects them into the LLM's system prompt or Tool-Calling schema. |

## 11. Tricky Questions & Edge Cases

Bro, what happens if the Stepwise planner gets stuck in an infinite loop?
It might call `SearchJira`, fail, call `SearchJira` again, fail, forever. To prevent your API bill from exploding, `FunctionCallingStepwisePlannerOptions` requires a `max_iterations` parameter (usually 5 or 10). If it hits that limit, it aborts and throws a `PlannerException`.

## 12. Real-World Usage

- **Automated Workflows**: A user types "Onboard new employee Alice". The planner orchestrates: `CreateADAccount(Alice)`, `AssignLaptop(Alice)`, `SendWelcomeEmail(Alice)`.
- **Data Analysts**: "Query the Q3 sales, plot it on a bar chart, and save it to my drive." The planner orchestrates SQL plugins, Matplotlib plugins, and File I/O plugins autonomously.

## 13. Best Practices
| DO | DON'T |
|---|---|
| Write extremely detailed `description` strings for your Plugins | Use vague names like "DoTask" |
| Limit the Kernel to only the Plugins needed for the task | Load 100 plugins and overwhelm the LLM's context window |
| Use Stepwise Planner for complex, unpredictable tasks | Use Handlebars Planner if API calls are likely to fail and require retry logic |

## 14. Production Notes
> Production Note:
> Relying purely on Planners in production is risky. Because it relies on the LLM's emergent reasoning, it is non-deterministic. For highly regulated enterprise pipelines (like Banking transactions), avoid Planners. Instead, hardcode the orchestration pipeline yourself using standard Python code, and only use the LLM for specific semantic transformations within that pipeline.

## 17. Advanced Planner Concepts
1. **Human-in-the-Loop (HITL)**: You can write a Native Plugin called `RequestHumanApproval`. If the Planner decides it needs to delete a database table, it calls that plugin, which halts execution, emails an admin, and waits for a webhook callback before the Planner resumes.
2. **Custom Prompts**: Planners rely on massive under-the-hood system prompts. If the planner is failing to utilize your specific plugins correctly, you can customize the planner's prompt template via the options configuration to give it specific instructions (e.g., "Always use the Database Plugin before the Email Plugin").

## 15. Common Mistakes
- **Poor Descriptions**: Giving a plugin the description "Searches stuff." The planner has no idea what it searches. Change it to: "Searches the internal Confluence wiki for HR policies."
- **Missing Parameters**: If your Native Plugin doesn't use python type hints (e.g., `def search(query: str):`), the planner generates a malformed schema, and the LLM will fail to pass the correct arguments.
