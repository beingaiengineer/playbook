## 4. Concept Explanation

LlamaIndex has evolved from just "Indexes" to full Agentic Orchestration.
1. **Query Engine Tools**: Wrapping your RAG pipelines into standard Tools that agents can call.
2. **FunctionCallingAgent**: An agent that uses OpenAI's native tool-calling capabilities to decide which Query Engine to use.
3. **Workflows (v0.10+)**: A modern, event-driven architecture. Instead of rigid DAGs, nodes emit `Events`, and other nodes listen for those events. This allows for incredibly flexible loops, human-in-the-loop, and parallel execution.

## 6. Beginner Example

Creating an Agent that has access to a calculator and a document query engine.

```python
# pip install llama-index
from llama_index.core.tools import FunctionTool
from llama_index.agent.openai import OpenAIAgent

# 1. Define a python tool
def multiply(a: int, b: int) -> int:
    """Multiplies two integers and returns the result."""
    return a * b

multiply_tool = FunctionTool.from_defaults(fn=multiply)

# (Assume `doc_tool` is a QueryEngineTool wrapping a PDF index)
# doc_tool = QueryEngineTool(...)

# 2. Create the Agent
agent = OpenAIAgent.from_tools(
    [multiply_tool], 
    system_prompt="You are a helpful assistant with a calculator.",
    verbose=True
)

# 3. Chat with the agent
response = agent.chat("What is 150 multiplied by 4?")
print(str(response)) # 600
```

## 7. Real-World Engineering Example

In modern LlamaIndex (v0.10+), you build **Workflows**. They use `@step` decorators and Python events to orchestrate complex multi-agent logic asynchronously.

```python
import asyncio
from llama_index.core.workflow import Event, StartEvent, StopEvent, Workflow, step

# 1. Define custom Events
class ReviewEvent(Event):
    code: str

# 2. Define the Workflow class
class CodeGenerationWorkflow(Workflow):
    
    # 3. Step 1: Triggered by StartEvent
    @step
    async def write_code(self, ev: StartEvent) -> ReviewEvent:
        print("Writing code for:", ev.prompt)
        # LLM Logic here...
        generated_code = "def hello(): print('world')"
        
        # Emits the ReviewEvent!
        return ReviewEvent(code=generated_code)
    
    # 4. Step 2: Listens for ReviewEvent
    @step
    async def review_code(self, ev: ReviewEvent) -> StopEvent:
        print("Reviewing code:", ev.code)
        # Review Logic here...
        
        # Emits StopEvent to end the workflow
        return StopEvent(result="Code Approved!")

async def main():
    wf = CodeGenerationWorkflow(timeout=60, verbose=True)
    result = await wf.run(prompt="Write a hello world function")
    print(result)

asyncio.run(main())
```

## 10. Top Interview Questions
| Question | Answer |
|---|---|
| Why did LlamaIndex pivot to Event-Driven Workflows? | Because rigid graphs (DAGs) are hard to manage when you have complex loops, parallel execution, or human-in-the-loop pauses. Events allow nodes to be completely decoupled. If Step A emits an Event, Step B, C, and D can all listen to it and run in parallel instantly. |
| What is a QueryEngineTool? | It is LlamaIndex's superpower. It wraps an entire RAG pipeline (embedder, retriever, synthesizer) into a single Tool with a description. The LLM can then decide *when* to execute a RAG search. |
| Can I use LlamaIndex Agents with local models? | Yes. You can swap the `OpenAIAgent` for `ReActAgent` which works seamlessly with local models like Llama-3 via Ollama, using string-based reasoning instead of OpenAI's proprietary JSON tool calls. |

## 11. Tricky Questions & Edge Cases

Bro, what happens if your Workflow emits an Event, but no `@step` is configured to listen to it?
The Workflow will hang! Because it is strictly event-driven, the system waits for a `StopEvent` to terminate. If an event is emitted into the void, the workflow pauses indefinitely until it hits the global `timeout` parameter and crashes. You must ensure all event pathways eventually route to a `StopEvent`.

## 12. Real-World Usage

- **Multi-Document Analysis**: A law firm uses LlamaIndex Agents to compare three different contracts. The Agent has a `QueryEngineTool` for each contract, autonomously queries each one, and synthesizes the differences.
- **Event-Driven AI Backends**: Using Workflows to handle incoming customer support emails. The `StartEvent` parses the email. It emits a `SearchKnowledgebaseEvent`, which triggers a RAG step. The RAG step emits a `DraftReplyEvent`, triggering the writer agent.

## 13. Best Practices
| DO | DON'T |
|---|---|
| Use Event-Driven Workflows for new production apps | Stick to legacy `AgentRunner` abstractions |
| Wrap RAG indexes cleanly into `QueryEngineTools` | Try to manually query the vector DB inside the agent loop |
| Use `PydanticProgram` for strictly typed outputs | Rely on raw string parsing for agent responses |

## 14. Production Notes
> Production Note:
> Event-driven architectures shine in scalable cloud environments. Because LlamaIndex Workflows use Python `asyncio` events, you can theoretically map these internal software events to external cloud events (like AWS EventBridge or Kafka topics), allowing distributed microservices to act as nodes in a massive AI workflow.

## 17. Advanced Routing (SubQuestionQueryEngine)
1. **Sub-Question Queries**: Before Workflows, LlamaIndex built massive agentic power via the `SubQuestionQueryEngine`. If a user asks, "Compare the revenue of Uber and Lyft in 2021", the engine autonomously splits the prompt into two sub-questions: "Uber 2021 revenue" and "Lyft 2021 revenue", executes them in parallel against different RAG tools, and merges the answers.
2. **Context Window Management**: LlamaIndex provides advanced memory modules (`ChatMemoryBuffer`) that automatically summarize or truncate chat history before it exceeds the LLM's context window, ensuring agents don't crash on turn 50 of a conversation.

## 15. Common Mistakes
- **Overloading Tools**: Giving an agent 30 different `QueryEngineTools`. The LLM's context window gets clogged with tool descriptions, and it hallucinates which tool to use. Use a `ToolRetriever` to dynamically fetch only the relevant tools based on the user's prompt.
- **Ignoring Async**: Writing synchronous blocking code inside an `@step` function. This freezes the entire Event loop and ruins the performance benefits of Workflows.
