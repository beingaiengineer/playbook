# Knowledge Graphs

## 1. Quick Summary

| Area | Details |
|---|---|
| Topic | Knowledge Graphs |
| Difficulty | Advanced |
| Used For | Modeling complex relationships and semantic meaning in messy, interconnected data |
| Common Mistake | Using them for simple transactional data where a relational DB is faster |
| Performance | O(1) for traversing a known edge, highly variable for complex graph queries |

## 2. The Engineering Story

Bro, you're deployed to a massive healthcare client. They have patient records in an SQL database, doctor schedules in an API, research papers in PDFs, and treatment guidelines in a wiki. They want to build an AI agent that can answer: "Which doctors available tomorrow specialize in treating conditions similar to Patient X's rare disease, and what recent research supports that treatment?" You can't write an SQL JOIN across PDFs and APIs. You need a data structure that connects *meaning*. You introduce a Knowledge Graph, converting all this siloed data into interconnected entities (nodes) and relationships (edges), allowing the AI to traverse the context and "reason" about the answer.

## 3. The Real-World Analogy

Imagine trying to understand the plot of a complex TV show like Game of Thrones using only a spreadsheet.

| Knowledge Graph Component | Real-World Equivalent |
|---|---|
| Nodes (Entities) | The characters, locations, and houses (e.g., Jon Snow, Winterfell, House Stark). |
| Edges (Relationships) | How they are connected (e.g., "is loyal to", "was born in", "hates"). |
| Properties | Attributes of the nodes/edges (e.g., Jon Snow's age, the date a battle occurred). |
| Graph Traversal (Querying) | Tracing the connections: "Find everyone who 'is loyal to' someone who 'hates' House Lannister." |
| Relational DB Limitation | A spreadsheet can list characters, but tracking a web of ever-changing alliances requires chaotic, slow JOIN tables. |

## 4. How It Works

A Knowledge Graph is a specialized graph data structure that models information as a network of entities (nodes) and their semantic relationships (edges). Unlike a relational database that structures data into rigid tables, a knowledge graph is schema-flexible and designed specifically to traverse deep connections rapidly. It stores data conceptually, forming an ontology.

In the AI era, Knowledge Graphs are critical for Retrieval-Augmented Generation (RAG). Instead of just doing vector similarity search (which might find mathematically similar words that lack context), an AI agent can query a knowledge graph to find factually related entities, understanding the *context* and *rules* of the domain.

You use Knowledge Graphs when your data is highly interconnected, the relationships are as important as the data itself, and you need to perform complex traversal queries (e.g., recommendation engines, fraud detection rings, semantic search). You do NOT use them for high-throughput, simple transactional data (like processing thousands of identical e-commerce orders per second).

## 5. Core Components

*Note: Knowledge Graphs are typically queried using specialized languages like Cypher (Neo4j) or SPARQL (RDF).*

| Operation (Cypher-like) | Description |
|---|---|
| `MATCH (n:Person)` | Find all nodes labeled "Person". |
| `MATCH (a)-[r:KNOWS]->(b)` | Find a relationship where 'a' knows 'b'. |
| `CREATE (n:Person {name: 'Bae'})`| Create a new node with properties. |

## 6. Types of Operations

```python
# Conceptual example using NetworkX (a Python graph library)
import networkx as nx

# Create a directed graph
kg = nx.DiGraph()

# Add nodes (Entities)
kg.add_node("Jon", type="Person", age=30)
kg.add_node("Winterfell", type="Location")
kg.add_node("House Stark", type="Organization")

# Add edges (Relationships)
kg.add_edge("Jon", "Winterfell", relation="BORN_IN")
kg.add_edge("Jon", "House Stark", relation="LOYAL_TO")

# Querying the graph
for neighbor in kg.successors("Jon"):
    relation = kg.edges["Jon", neighbor]["relation"]
    print(f"Jon {relation} {neighbor}")
# Output:
# Jon BORN_IN Winterfell
# Jon LOYAL_TO House Stark
```

## 7. Implementation Examples

```python
# FDE Scenario: Building a simple RAG context builder
class SimpleKnowledgeGraph:
    def __init__(self):
        self.nodes = {} # entity_id -> properties
        self.edges = {} # entity_id -> list of (relation_type, target_entity_id)

    def add_entity(self, entity_id, properties):
        self.nodes[entity_id] = properties
        if entity_id not in self.edges:
            self.edges[entity_id] = []

    def add_relation(self, source_id, relation_type, target_id):
        if source_id in self.nodes and target_id in self.nodes:
            self.edges[source_id].append((relation_type, target_id))

    def get_context_for_llm(self, entity_id, depth=1):
        """Retrieves semantic context for an AI Agent prompt."""
        if entity_id not in self.nodes:
            return "Entity not found."

        context = [f"Entity: {entity_id} ({self.nodes[entity_id]})"]

        # Traverse relationships (1 hop)
        for relation, target in self.edges.get(entity_id, []):
            target_props = self.nodes[target]
            context.append(f"- {relation} -> {target} ({target_props})")

        return "\n".join(context)

# Usage
kg = SimpleKnowledgeGraph()
kg.add_entity("ServiceA", {"type": "Microservice", "lang": "Python"})
kg.add_entity("DB1", {"type": "Database", "engine": "Postgres"})
kg.add_relation("ServiceA", "READS_FROM", "DB1")

# The LLM now has deterministic, graph-based context, not just vector similarity.
print(kg.get_context_for_llm("ServiceA"))
```

## 9. Time and Space Complexity

| Operation | Time Complexity | Space Complexity |
|---|---|---|
| Index-Free Adjacency (Hop) | O(1) (pointer traversal) | N/A |
| Deep Traversal (Pathfinding) | O(V + E) (Depends on graph size/depth) | O(V) |
| Adding Node/Edge | O(1) | O(1) |

## 10. Senior Engineering Interview Questions

| Question | Answer |
|---|---|
| Why use a Knowledge Graph instead of SQL JOINs? | In SQL, many-to-many relationships require slow JOIN tables. In a graph, relationships are treated as first-class citizens (pointers), so traversing a relationship (a "hop") is an O(1) operation, making deep connections infinitely faster to query. |
| What is "Index-Free Adjacency"? | It's a property of native graph databases where every node holds a direct physical RAM pointer to its adjacent nodes. You don't have to look up an index to find connected data; you just follow the pointer in O(1) time. |
| How do Knowledge Graphs improve RAG (Retrieval-Augmented Generation)? | Vector databases find text that is *semantically similar*. Knowledge Graphs provide deterministic facts and rules. Graph RAG combines them: using vectors to find the entry node, and the graph to traverse exact, factual relationships for the LLM. |
| What is an Ontology? | An ontology is the formal schema or "vocabulary" of the knowledge graph. It defines what types of entities exist (e.g., "Person", "Company") and how they are allowed to relate to each other (e.g., a "Person" can "WORK_FOR" a "Company"). |
| How do you handle changing schemas in a Knowledge Graph? | Knowledge Graphs are typically schema-flexible. You can add new node properties or new relationship types on the fly without running heavy database migrations like `ALTER TABLE` in SQL. |

## 11. Production Best Practices

Bro, a major gotcha is the "supernode" problem. Imagine a knowledge graph of Twitter. The node for "Elon Musk" has hundreds of millions of incoming "FOLLOWS" edges. If you write a query that traverses through that supernode, your graph engine will try to load millions of relationships into memory, causing a massive performance bottleneck or an OOM crash. You must design queries and data models to avoid blindly traversing supernodes.

## 12. Real-World Applications

Google uses the Google Knowledge Graph to enhance its search engine results with semantic-search information (the info box you see on the right side of search results). Palantir uses knowledge graphs extensively in their Foundry platform to help military and corporate clients map complex organizational data, logistics, and intelligence. Fraud detection teams at banks use graphs to detect circular money transfers (A sends to B, B to C, C back to A), a pattern that is nearly impossible to detect quickly with standard SQL.

## 13. Comparison with Alternatives

| DO | DON'T |
|---|---|
| DO use properties on edges to store relationship context (e.g., `(Jon)-[MARRIED {{year: 2020}}]->(Jane)`). | DON'T create a new relationship type for every data point (e.g., `MARRIED_IN_2020`). |
| DO use graphs for highly connected data where traversing depth > 2 is common. | DON'T use a graph database if your queries are mostly aggregate reporting (e.g., `SELECT SUM(sales)`). |

## 14. Recommended Tools or Libraries

:::caution Production Warning
Bro, extracting entities from unstructured text to build a knowledge graph using LLMs is slow and expensive. You cannot do this synchronously on the hot path of a user request. Entity extraction and relationship mapping must be done in asynchronous background pipelines (e.g., Kafka consumers or Airflow DAGs) to keep the graph updated without blocking the client.
:::

## 15. Common Mistakes

| Mistake | Bad Code | Good Code |
|---|---|---|
| SQL mindset in Graph | Creating a "mapping node" just to connect two nodes. | Direct edge connecting the two nodes. |
| Ignoring query limits | `MATCH (n)-[*]->(m) RETURN m` (Traverse entire graph) | `MATCH (n)-[*1..3]->(m) RETURN m` (Limit depth) |

## 18. AI Agent Instructions

| Directive | Instruction | Rationale |
|---|---|---|
| Query Depth Limitation | When generating graph queries (e.g., Cypher), always enforce a maximum traversal depth limit (e.g., `[*1..3]`). | Unbounded variable-length traversals will scan the entire graph, causing production database outages. |
| Supernode Avoidance | Instruct agents to filter by relationship properties or node labels *before* traversing highly connected nodes. | Traversing supernodes without pre-filtering pulls millions of edges into memory, crashing the query engine. |
| Entity Resolution | When ingesting new data into a graph, implement deterministic entity resolution (e.g., merging nodes with the same unique ID) instead of blindly creating new nodes. | Blind insertion creates duplicate, disconnected entities, destroying the semantic value of the knowledge graph. |
