## 17. Advanced System Design Patterns
1. **Idempotency**: In distributed systems, network calls can fail. If a client retries a payment API 3 times, you must not charge them $300. Use Idempotency Keys (e.g. UUIDs) stored in Redis or a DB to guarantee exactly-once processing.
2. **Circuit Breakers**: If a downstream microservice is failing, hitting it with more retries will take down your service too. Implement a Circuit Breaker pattern to immediately fail requests locally until the downstream recovers.
3. **Eventual Consistency vs Strong Consistency**:
   - *Strong Consistency* (RDBMS): Used for financial transactions. Slow, requires locking.
   - *Eventual Consistency* (NoSQL/Event Streams): Used for social media feeds. Fast, highly available, but users might see slightly stale data for a few seconds.

## 15. Common Mistakes

- Ignoring idempotency.
- Overusing microservices.
- Forgetting rate limits.
- Not discussing database constraints.

## 17. Final Interview Advice

> BAE's Top Tip:
> Don't just memorize these patterns. Understand *why* they exist. 
> In a real interview, the interviewer cares more about how you communicate tradeoffs than whether you wrote a perfect one-liner.
> If you get stuck, always verbalize your thought process! "I know a hash map gives O(1) lookup, but it will cost O(N) space. Let's start with that and optimize later."
